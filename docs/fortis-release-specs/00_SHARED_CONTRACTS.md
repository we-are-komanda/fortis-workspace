# Общие контракты релизного пакета Fortis

**Статус:** предлагаемые уточнения от 20 сентября 2026 года. Согласованная реализация должна зафиксировать их в knowledge-base; этот файл сам по себе не меняет принятые ADR.

## 1. Цель и явно ограниченный результат

Первый релиз этого пакета — **закрытая рабочая версия для подготовки, сохранения, сравнения и документирования конфигураций и бюджета**. Это не приёмка всех пунктов исходного ТЗ.

Сохраняем `DefenseProject`, существующий 2D GIS, текущий интерфейс, раздельные submodules, Next.js/React/Go/PostgreSQL. Не строим заново библиотеку, карту, login или save/load, если их поведение уже соответствует критериям.

Из предложенной Spec 03 берём server-backed workflow, бюджет, версии и отчёт. Её spatial evaluation, остаточный риск и сравнение физической эффективности остаются вне пакета вместе с P2/P3. Нельзя скрыть эту разницу под статусом «полностью соответствует первому этапу ТЗ». Полноту исходного ТЗ ведём отдельно.

Не добавляем расчёты применения оружия, перехвата, подавления, вероятностей поражения, новые алгоритмы размещения и эффективности. Существующие пользовательские данные геометрии только сохраняются и отображаются; их инженерная достоверность не улучшается и не заявляется этим пакетом.

## 2. Рабочие решения, зафиксированные для кодеров

| Тема | Решение пакета | Что уже поддержано источником |
|---|---|---|
| Доступ | Закрытое подключение клиентов; минимальные роли admin/editor/viewer на предприятие | Доступ по предприятиям — ТЗ; роли и закрытое подключение — конкретизация пакета |
| Хранение | Текущий проект + неизменяемая ревизия каждого успешно сохранённого состояния | Версия и optimistic locking уже есть; неизменяемая история — предлагаемое расширение |
| Стоимость | RUB, точная арифметика в копейках; суммы из строк размещённых объектов | Единый расчёт — roadmap; формат minor units — техническое решение пакета |
| Бюджет | `limited` с жёстким запретом либо `unlimited`; без скрытого soft override | Пример жёсткого лимита — ТЗ; выбор одного режима для релиза — конкретизация |
| Отчёт | Официальный экспорт только из сохранённой ревизии и серверного payload | Прямо предложено в Spec 00/03 |
| Черновик | Локальное восстановление, ручное сохранение на сервер, отсутствие silent overwrite | ADR-0010 и Spec 00 |
| Demo | Явный режим; отдельные cookie/session и storage; никакой автоматической подмены | Различие demo/runtime и рабочего проекта — источники |
| Проверки | Unit + API с реальной БД + браузерный путь с настоящим backend | Матрица и E2E предусмотрены Spec 00/03 |

Все новые пороги — внутренние критерии приёмки, а не опубликованный SLA.

## 3. Единицы, поля и совместимость

`DefenseProject.schemaVersion=1` не означает наличия всех новых DTO. Не повышать schemaVersion механически ради envelope, бюджета или хранения ревизий. Добавления к проекту делаем совместимыми и описываем миграцию старых snapshots. При действительно несовместимом изменении — отдельное решение о schemaVersion и тест импорта.

Сохраняем имеющиеся URL API. Backend использует query-параметры для идентификаторов, list `limit/offset/totalItems`. Дополнительные поля вводятся явно, не подмена серверных DTO frontend-константами. Existing `version` остаётся ожидаемой версией для `PUT /projects/update`.

В server-backed изменяющем запросе `version` обязателен. Отсутствие → 400 `version_required`, несовпадение → 409 `version_conflict`; состояние БД не меняется. Для создания нового проекта ожидаемая версия не нужна.

Старый клиент, не передающий version, после включения production gate не получает право на silent overwrite. Развёртывание: совместимый сервер → обновлённый frontend → проверка → включение обязательной version. Переходный режим разрешён только на изолированном тестовом окружении, не с клиентскими данными.

Данные библиотечных дальностей на существующей границе км/м не конвертируются повторно. Этот пакет тестирует round-trip единиц, но не меняет методики покрытия.

## 4. Идентичность расчётного результата

Каждый результат `cost`, `budget`, `compare`, `report` несёт:

```ts
type CalculationIdentity = {
  projectId: string;
  projectVersion: number;
  calculationVersion: string;
  inputDataVersions: Record<string, string>;
  snapshotDigest: string;
};
```

Объект идентичности размещается в ответе как `identity` новым additive-полем. Старые денежные поля могут временно существовать как производные для миграции, но новый UI читает только новый контракт. Digest вычисляется сервером по описанным ниже правилам; в коде не хранится пример вместо реального значения.

`projectVersion` — серверная ревизия, а не timestamp, число изменений браузера или версия каталога. `calculationVersion` меняется при изменении алгоритма округления/агрегации. `inputDataVersions` перечисляет зафиксированные наборы, фактически вошедшие в расчёт; для отсутствующего внешнего источника не выдумывается версия.

`snapshotDigest` вычисляется по замороженному server payload проекта, библиотечного снимка и бюджета: UTF-8 JSON, ключи объектов сортируются рекурсивно, порядок массивов сохраняется. Транспортные `requestId/generatedAt` не входят. Digest идентифицирует содержимое, но не является электронной подписью или заменой контроля доступа.

На frontend:
- сохранённое состояние читает серверную проекцию той же identity;
- локальное редактирование показывает целиком локальный preview с явной меткой «Черновой расчёт»;
- нельзя брать objectLines из draft и total из другой server revision;
- ответ запроса к проекту A не применяется после перехода в B;
- старый ответ версии N не заменяет результат версии N+1.

## 5. Сохранение и ревизии

Новые хранилища/объекты пакета:
- `project_revisions(project_id, version, snapshot_json, created_at, created_by, snapshot_digest)` с unique `(project_id,version)`. Сохраняется полная совместимая структура, включая budget snapshot и использованные данные каталога. JSONB — существующая инфраструктурная конвенция.
- `snapshot_json` имеет envelope `{project, budget, inputDataVersions}`. `project` — существующий DefenseProject, а не новая параллельная доменная модель.
- `version` текущего проекта, данные проекта, его бюджет и новая ревизия меняются атомарно. Неизменяемые ревизии не обновляются задним числом.
- Авторитетный финансовый результат с identity сохраняется/кешируется по `(project_id,version,calculation_version)`. Старый выпущенный отчёт не пересчитывается новым алгоритмом молча.

Для существующих проектов FRC-04 создаёт **только снимок текущей известной версии**. Историю до миграции не восстанавливает фиктивно. Запрос отсутствующей ревизии → 404 `revision_not_found`.

`POST /api/v1/projects` и импорт создают новый проект/вариант. Идемпотентность при повторе запроса обеспечивается `Idempotency-Key`, scoped по пользователю/операции, TTL 24 часа. Тот же ключ и те же данные возвращают прежний результат, другой payload с тем же ключом → 409 `idempotency_conflict`. Проверка текущих прав выполняется и при повторе.

После потери ответа на успешный update нельзя молча повторять запись с новой версией. Клиент читает актуальную ревизию и сравнивает её с отправленной; при отличии показывает конфликт. Локальные изменения, внесённые после старта save, не исчезают.

## 6. Финансовый контракт

Новый формат на финансовой границе: `Money = { currency: "RUB", minor: string }`, где `minor` — целое десятичное количество копеек. Рабочая арифметика: integer/decimal, не двоичные float-суммы.

Конверсия существующих `*Mln`: 1 млн руб. = 100 000 000 коп. Миграция парсит исходное JSON decimal-представление и округляет до копейки `half-up` ровно один раз на единичной цене. Округлённые/неоднозначные значения сопровождаются validation warning; `null` не равен 0. Legacy numeric-поля — только адаптер совместимости.

Количество — целое 1…1 000 000 для размещённой единицы. Удаление — отдельная операция; отрицательные, NaN и дробные количества → 400. Цена — 0…10^15 коп. за единицу; итог хранится в NUMERIC и возвращается строкой, чтобы не переполнить JSON number. Эти пределы — ограничения продукта, не цены реального оборудования.

Приоритет цены: явная instance override, включая ноль → сумма компонентов при явном `pricingMode=components` → зафиксированная единичная цена шаблона. Сложение компонентной суммы и bundle-цены запрещено. При `components` override заменяет итог комплекта, а не прибавляется к нему. Персонал без заданной периодики/цены не считается «бесплатным»: стоимость неизвестна либо не входит в обозначенный состав расчёта.

Суммы группируются по реальным `project.layers[].id` и текущим типам; mapping на старые 8 эшелонов не участвует. Видимость на карте не исключает строку из стоимости. `inactive/maintenance` — не автоматическое исключение из сметы. Иные правила OPEX/амортизации/НДС этот релиз не изобретает. Метка сметы: «По указанным ценам; налоги, монтаж и эксплуатация учтены только при явном включении в строки».

Если цена неизвестна: `lineTotalMinor=null`, `totalMinor=null`, `knownSubtotalMinor` содержит сумму известных строк, `isComplete=false`. В `BudgetProjection` при неполном итоге status=`indeterminate`; иначе unlimited→`unlimited`, limited и итог≤лимита→`within_limit`, historical limited с превышением→`exceeded`. `remainingMinor=null` для unlimited или неполного итога. UI показывает «Итог неполный», а не ноль/точный бюджет. В limited-режиме нельзя сохранить новое состояние с неизвестной ценой; в unlimited допускается предварительный документ с явным предупреждением.

## 7. API-дополнения пакета

| Операция | Контракт пакета |
|---|---|
| GET `/api/v1/projects/get?id=P&projectVersion=V` | Текущая либо указанная сохранённая версия; old API без V возвращает current. Указанная отсутствующая версия не заменяется current |
| PUT `/api/v1/projects/update?id=P` | Existing `{name, enterpriseId, projectJson, version}`; для релизного клиента version обязательна |
| GET `/api/v1/projects/cost?projectId=P&projectVersion=V` | `CostProjection`, точная identity |
| PUT `/api/v1/projects/budget?projectId=P` | `{version,budgetMode,budgetLimitMinor}`; unlimited → limit null; меняет общую revision атомарно |
| POST `/api/v1/projects/budget/check?projectId=P` | `{version,projectJson}` — preflight полного кандидата; не записывает его, не резервирует остаток |
| GET `/api/v1/projects/budget?projectId=P&projectVersion=V` | BudgetProjection данной ревизии, не текущий бюджет для старого отчёта |
| GET `/api/v1/projects/compare` | Предлагаемые query `projectIdA,projectVersionA,projectIdB,projectVersionB`; existing aliases адаптировать явно в FRC-00/08; обе стороны должны принадлежать одному предприятию |
| GET `/api/v1/projects/report?id=P&projectVersion=V&hideCost=true|false` | Отчёт конкретной ревизии, с безопасной проекцией полей |
| POST `/api/public/demo-requests` | Новый same-origin BFF: публичная заявка; BE новый POST `/api/v1/demo-requests` |

Версии в расчётных запросах обязательны для релизного клиента. Кодер фиксирует текущие DTO перед расширением; таблица не утверждает, что новые параметры уже поддерживаются. Финальная OpenAPI — часть FRC-04/07/08/10/12.

## 8. Ошибки и режимы

Единый envelope:
```json
{"error":{"code":"version_conflict","message":"Project version conflict","requestId":"req-uuid","retryable":false,"details":{"expectedVersion":7,"currentVersion":8}}}
```

400 — invalid input/version_required; 401 — нет/истекла сессия; 403 — роль не разрешает действие внутри доступного предприятия; 404 — несуществующий либо недоступный конкретный ресурс; 409 — конфликт версии/идемпотентности; 422 — бюджетный запрет; 429 — лимит запросов; 502 — некорректный upstream ответ; 503 — upstream недоступен/configuration unavailable; 504 — истёк таймаут. `requestId` не несёт пользовательские данные.

Отсутствие данных → `200 {items:[], totalItems:0}`, а не ошибка и не mock. Для server-backed проекта на 401/403/404/5xx запрещено возвращать demo payload с 200.

`FORTIS_RUNTIME_MODE=demo|workspace` — предлагаемая явная серверная настройка; frontend узнаёт только безопасный режим через конфигурацию. Флаг из query/localStorage не включает demo backend. Production допускает только workspace с включёнными guards. Demo и workspace имеют разные origin/session cookies и namespaces storage. Перенос проекта из demo — только явный импорт с валидацией и сохранением качества `demo`.

## 9. Состояния пользовательского проекта

`loading`, `saved`, `dirty`, `saving`, `offline_draft`, `conflict`, `error`. Dirty определяется изменением бизнес-содержимого относительно saved snapshot, а не одним `updatedAt`: выбор строки, темы, панели, активного фильтра и навигация сами по себе не создают новую финансовую версию.

Draft ключ: `fortis:draft:<userId>:<enterpriseId>:<projectId-or-localId>`. Токены туда не попадают. Старый общий ключ автоматически не присваивается новому пользователю. Содержимое чужого локального draft не должно отображаться после смены аккаунта. Для shared-device режима локальное длительное хранение отключается настройкой поставки.

Два браузера с N: первый save → N+1, второй save → 409. Второй draft остаётся; действия «Открыть серверную версию» после явного подтверждения потери локальных изменений, «Сохранить отдельным вариантом» при сохранённом праве записи. Автоматический merge не нужен.

## 10. Минимальная модель доступа

Admin предприятия: назначение членов, редактирование, библиотека/документы, экспорт. Editor: проект/варианты/каталог своего предприятия, отчёт; не выдаёт себе роли. Viewer: чтение и экспорт разрешённых данных, без изменений. Доступ к ценам: отдельная capability `viewCost`; viewer без неё получает только серверно урезанные ответы.

Публичные шаблоны общие на чтение; правка — у платформенного администратора. Приватная библиотека и её документы наследуют enterprise access. Бэкенд проверяет resource ownership по сохранённому объекту, а не доверяет enterpriseId из запроса. Отзыв доступа действует на следующем запросе, а не только после истечения JWT.

Это конкретизация ТЗ и ADR, не утверждение, что такие роли уже реализованы. Самостоятельной регистрации клиентов в первом релизе нет; первоначальные пользователи и предприятия выдаются через ограниченный административный процесс FRC-02/03.

## 11. Общая приёмка

В каждой задаче различать: реализовано, проверено unit, проверено API, проверено server-backed E2E, принято. Уже выполненную задачу закрывать проверкой, не новым переписыванием. Непроверенные бюджет, изоляция, восстановление и отчёт — release blockers.

Тестовые данные синтетические; никакого клиентского объекта, реальных учётных данных или реального оборудования с параметрами применения в fixtures. Нагрузочные/отрицательные тесты — только в изолированном окружении.

## 12. Журнал действий

Для значимых изменений создаётся `AuditEvent`: eventId, actorId, enterpriseId, entityType, entityId, action, previousVersion, newVersion, occurredAt, requestId. Сырые payload, пароли, токены, email, карты и суммы не входят в общий журнал. ActorId определяется сессией, не телом запроса.

FRC-02 создаёт минимальный append-only для приложения журнал `audit_events` в owning backend-модуле и записывает изменения membership/session. FRC-04/07/09 используют тот же журнал для save/import/delete, изменения бюджета и операций с документами. Успешные изменения фиксируются в той же транзакции; неуспешные попытки авторизации идут в отдельный очищенный security-log. Append-only не означает сертифицированную защиту от администратора БД.
