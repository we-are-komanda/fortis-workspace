# Fortis — спецификации для закрытия пробелов перед запуском

**Дата:** 20 сентября 2026 года. **Статус:** пакет предлагаемых спецификаций, не реализация и не приёмка продукта.

Пакет содержит **15 самостоятельных задач**, общий FE/BE контракт, синтетический финансовый эталон, матрицу покрытия аудита и правила выдачи работы кодеру. Репозитории/Linear/deployment этим пакетом не изменены.

## Что передать исполнителю

Одна задача из `specs/` + `00_SHARED_CONTRACTS.md` + `contracts/release-contracts.ts` + `fixtures/finance-v1.json` + `SOURCES.md`. Универсальная инструкция — [CODER_PROMPT.md](CODER_PROMPT.md). Работать без общего контракта только по заголовку тикета нельзя.

Прочитать сначала [общие контракты](00_SHARED_CONTRACTS.md), затем [FRC-00](specs/FRC-00_release_baseline.md). Не начинать с нового UI или переписывания save/load: часть функций уже реализована.

## Граница релиза

**Объект → текущая конфигурация → надёжное сохранение → одна версия расчёта → сравнение → воспроизводимый отчёт.**

Закрытое подключение первых клиентов; 2D GIS и существующая модель DefenseProject. Без новых алгоритмов применения оборудования, сценарного/ретроспективного модуля, 3D-переработки, healthbar и обещаний реальной эффективности.

Это сознательно ограниченный релиз, **не полное выполнение всего исходного ТЗ**. Более широкие предложенные Spec 00/01/03 в базе знаний не стираются. Наши ограничения и архитектурные конкретизации должны быть записаны в knowledge-base, а не приняты молча за прежние договорённости.

## Порядок выполнения и параллельная работа

1. **Основание:** FRC-00. Одновременно начать подготовку CI и инфраструктурных решений FRC-13/14: окружение, доступы, хранение, scanner, уведомления, политика данных.
2. **Рабочий API:** FRC-01. Параллельно готовить копию/маршруты FRC-11 и серверный приём заявок FRC-12.
3. **Права:** FRC-02. Фронтенд отдельно может воспроизвести фильтр FRC-03, но весь первый пользовательский путь принимается позже.
4. **Сохранённая версия:** FRC-04. Затем параллельно FRC-05 (стоимость) и FRC-09 (источники/документы).
5. **Сохранение в интерфейсе:** FRC-06. Затем FRC-03 (полный старт проекта) и FRC-07 (бюджет).
6. **Результат для клиента:** FRC-08 (сравнение) и FRC-10 (отчёт); их зависимости указаны в реестре.
7. **Приёмка:** завершить FRC-13 на интегрированном release candidate, затем FRC-14 go/no-go.

FRC-13/14 — не задачи «подождать до конца». Их подготовка идёт с первого этапа; зависимости относятся к финальной приёмке. В частности, storage/scanner/notification выбираются и настраиваются до приёмки FRC-09/12, а не после неё.

FE/BE разработка может идти параллельно только после фиксации DTO и сценариев ошибки. Изолированные UI-моки допустимы для разработки, но не засчитываются как server-backed acceptance.

## Что является новым решением этого пакета

Неизменяемые ревизии, точные денежные minor units, минимальные роли, закрытый onboarding, hard budget gate, безопасная unpriced projection, durable lead/outbox, стартовые технические пороги. Это предлагаемые способы закрытия аудита, а не найденные в коде готовые возможности.

Исторические FRT связывать с задачами после чтения текущего tracker. Здесь их статусы не проверены, новые тикеты не созданы и существующие не закрыты.
