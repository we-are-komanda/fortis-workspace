# Инструкция для кодера: одна задача за проход

Передать кодеру этот текст вместе с одной конкретной FRC-спекой и общими контрактами. Не передавать все задачи одновременно как один запрос «сделай всё».

> Ты работаешь в существующем Fortis workspace. Задача — выполнить приложенную FRC-спецификацию, не переписывая продукт и не расширяя scope.
>
> Прочитай AGENTS.md, knowledge-base/00_Index.md, действующий roadmap, релевантные ADR, release manifest FRC-00 и 00_SHARED_CONTRACTS.md. Отдельно различай принятые ADR, предложенные спецификации и исторические заметки. Проверь git status всех затрагиваемых репозиториев. Не делай pull/reset/checkout поверх чужих изменений.
>
> Сначала установи фактическое состояние. Если функция уже работает, добавь/запусти недостающие доказательства и не реализуй её второй раз. У каждого утверждения «исправлено» должен быть воспроизводимый тест на конкретном SHA. Наблюдения прежнего аудита не являются уже подтверждёнными сегодняшними дефектами.
>
> Работай только в owning submodule. Не переносить исходники между frontend/backend/parent. Перед изменением Next.js API прочитай локальные docs установленной версии. Новые DTO из пакета — предлагаемый контракт: сверь существующие поля, сохрани совместимость и документируй миграцию. Не создавай второй источник истины вместо DefenseProject.
>
> Реализуй задачу небольшими изменениями: поведенческий тест → подтверждение падения для нового поведения → минимальное исправление → тест → проверка смежных сценариев. Для автономной реализации применяй доступный workflow executing-plans/subagent-driven-development; выбор workflow не разрешает менять продуктовую задачу. Не объявляй независимый review, если его не было.
>
> Не добавляй скрытые mock fallback в workspace, silent overwrite, price null→0, пропуск проверки прав, fake success формы или игнорирование CI. Не внедряй расчёты реальной эффективности оборудования, моделирование атак, 3D или новый дизайн.
>
> При конфликте требований не выбирать удобное поведение молча. Приведи точные источники, сформулируй различие и запиши блокер/предложение в acceptance matrix; не помечай незавершённую задачу принятой. Выполни независимую неблокированную часть. Для инфраструктуры не выдавай выдуманные credentials, URL, права или политику retention.
>
> В завершение предоставь: изменённые файлы и причины; принятые DTO/миграции; команды и фактические результаты unit/integration/build/E2E; SHA каждого репозитория; результаты каждого acceptance ID из спеки; оставшиеся ограничения и способ rollback. Если тест не запускался, напиши это прямо. Ничего не деплой, не оплачивай и не меняй доступы реального клиента без разрешения.
>
> Обнови релевантную knowledge-base и матрицу. Child commits идут первыми, parent pointers — отдельным согласованным изменением после них. Функция не считается завершённой только потому, что её кнопка появилась в UI.
