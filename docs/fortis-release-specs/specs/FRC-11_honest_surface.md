# FRC-11. Честные обещания, навигация и отделение демонстрации

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Frontend + product owner.
**Зависимости для приёмки:** FRC-00, FRC-01.
**Цель:** Публичные страницы и рабочий интерфейс описывают фактический релиз, а не функции будущей оперативной платформы.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

Прошлый аудит показал несоответствие лендинга GIS scope и неподтверждённые количественные обещания. Roadmap явно исключает ретроспективу/сценарии из critical path; operational dashboard обозначен mock в историческом контексте. Перед изменением кодер проверяет текущие тексты/маршруты.

Источники: [S4], [S6], [S2]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `src/modules/home/ui/home-page.tsx`, `src/modules/dashboard/`, `src/modules/drone-defense/ui/defense-studio-shell.tsx`, auth/landing links, existing mock data imports/routes.
Новые: `src/shared/config/product-capabilities.ts`, `src/modules/home/ui/release-copy.test.ts`; knowledge-base — принятый текст позиционирования и capability matrix.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Один capability manifest отделяет `available`, `demo`, `not_released`. Server runtime mode определяет разрешённые маршруты; manifest не является механизмом авторизации. Production workspace не импортирует mock operational state как customer data.

## 4. Требуемое поведение

1. Рабочий заголовок: «Планирование конфигураций и бюджета безопасности объекта». Подзаголовок: «Соберите конфигурацию на карте, сравните сохранённые варианты и подготовьте отчёт для согласования». Это предложенная точная копия, не утверждение о доказанном сокращении расходов.
2. Оставить проверяемые возможности: конфигурация на карте, собственные исходные данные, расчёт по введённым ценам, сохранение версий, сравнение и отчёт. До приёмки конкретной функции не писать «уже доступно».
3. Удалить/снять с рабочего лендинга неподтверждённые проценты, SLA/uptime, время обнаружения, гарантии отсутствия слепых зон, самообучение, автоматическое улучшение реальной защиты, интеграции с брендами без проверенного коннектора. Не заменять их другими придуманных цифрами.
4. CTA: «Войти в рабочую зону» и «Запросить демонстрацию». Форма показывает успех только по FRC-12. До его завершения не публиковать ложный приём заявок.
5. Рабочая навигация приводит к enterprise/project workflow. Mock `/dashboard` страницы с метриками и неподключённые operational модули в workspace-mode недоступны прямым URL либо имеют явную служебную заглушку без чисел; одного удаления меню недостаточно.
6. Отдельный demo-origin/режим может показывать синтетические данные, но с постоянной меткой «Демонстрационные данные». Пользователь не может принять demo объект/число за свой проект.
7. В калькуляторе заменить технические сообщения «backend…» пользовательскими, сохранив requestId для поддержки. Не удалять информацию о неполноте/черновике ради эстетики.
8. Не переделывать GIS UI в другой стиль. Сохранить актуальный runtime-дизайн; история UI Kit/отката не является приглашением повторить редизайн.
9. Важное ограничение продукта в доступном тексте: «Расчёт составляется по введённым данным и не подтверждает фактическую эффективность системы безопасности».

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| COPY-01 | Поиск неподтверждённых SLA/accuracy/экономии/zero blind spots в rendered страницах | Их нет на release surface |
| COPY-02 | Main CTA нового пользователя | Ведёт к корректному login/workspace, не mock dashboard |
| COPY-03 | Прямое открытие unreleased operational route | Нет customer-like mock данных |
| COPY-04 | Demo-origin | Постоянная demo-метка, отдельные session/storage |
| COPY-05 | Ошибка API в рабочем интерфейсе | Понятная ошибка, не fake success и не сырой stack |
| COPY-06 | Desktop 1280×720 / 1440×960 | Существующий рабочий дизайн не регрессировал |
| COPY-07 | Функция ещё не принята | Не включена как released только потому, что есть button |

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Новый бренд, полный визуальный редизайн, разработка оперативных функций, публикация новых маркетинговых метрик без измерений.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
