# FRC-02. Сессии, доступ к предприятиям и изоляция данных

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Backend + frontend auth + QA.
**Зависимости для приёмки:** FRC-00, FRC-01.
**Цель:** Пользователь получает только разрешённые ему данные и действия, включая API, snapshots, документы и экспорт.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

ADR-0010 уже требует HttpOnly auth, защищённые `/prototype`, `/calculator`, `/workspace`. Прошлый аудит обнаружил более узкий route guard; актуальное исполнение auth на сервере в этом ходе не проверялось. Это задача проверки и закрытия пробелов, а не утверждение, что JWT отсутствует.

Источники: [S1 раздел III], [S9], [S4], [E1], [E2]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `src/proxy.ts`, `src/app/api/auth/*/route.ts`, `src/modules/auth/`, project store и query cache; новые `src/modules/auth/model/release-access.test.ts`.
BE: `internal/middleware/auth.go`, user/enterprise application services, project/asset/document/budget/report controllers, DI/router; существующие membership migrations. Новые permission tests в соответствующих application-модулях; integration `tests/integration/release_access_test.go`.
Новый BE-модуль `internal/modules/audit/` и миграция `audit_events` реализуют контракт журнала из общего документа.

Дополнительные колонки роли/capability или session version — только миграцией, не editing production rows вручную.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Минимальные `EnterpriseRole` и `viewCost` — общие контракты. Admin/editor всегда имеют viewCost; ограничение финансов применяется к viewer. Backend security decision использует аутентифицированный userId и persisted ownership конкретного ресурса. `next` разрешает только локальные нормализованные пути из разрешённого набора.

## 4. Требуемое поведение

1. Закрыть три рабочие страницы route guard, но каждое API независимо проверяет сессию и resource permission. Наличие cookie не означает валидную сессию.
2. HttpOnly, Secure в production, SameSite для same-origin auth. Токены не возвращать в JS/session storage. Logout отзывает текущую серверную сессию либо session version; очистка cookie не является единственным механизмом отзыва. Проверять origin/CSRF для изменяющих browser-запросов по принятой схеме.
3. Все list/get/create/update/delete/import/export/compare/report/budget/document endpoints проверяют принадлежность предприятия. Проверка одного enterprise endpoint не защищает projects. Ни ID в URL, ни enterpriseId в теле не дают доступа.
4. Доступ к чужому/несуществующему ресурсу — одинаковый 404; запрещённое действие внутри доступного предприятия — 403. Ошибка не раскрывает имя/сумму чужого проекта. Проверить обе стороны compare и parent документа.
5. Membership проверяется на каждом доступе; отзыв права действует на следующем запросе. Полный snapshot, в том числе raw JSON export и библиотечные цены, недоступен viewer без viewCost: только allowlisted unpriced projection. Cost/budget/прямой raw export для него → 403.
6. Кеши ключуются по userId + enterpriseId + projectId + version. На logout/switch account очищаются in-memory state, query cache и пользовательское local storage согласно политике recovery. Broadcast между вкладками прекращает отображение старой сессии.
7. Закрытый onboarding: production public register отключён понятным экраном; первоначальный администратор создаётся ограниченной служебной командой без пароля в Git, без входящего публичного bootstrap endpoint. Существующим утверждённым admin-процессом выдаются аккаунты/роли. Ввод/сброс пароля — через защищённый операторский процесс до появления self-service.
8. Добавить ограничения попыток входа/регистрации и безопасные сообщения. Не позволять запросом роли повысить привилегии. Обычная user invitation/SSO инфраструктура в этот релиз не требуется.
9. Записывать membership/session изменения в минимальный журнал AuditEvent; права на чтение журнала только у уполномоченного администратора.
10. В отчёт об исправлении включить матрицу разрешений, а не только скриншот login.

## 5. Приёмка и регрессионные сценарии

| ID | Проверка | Ожидание |
|---|---|---|
| AUTH-01 | Нет, поддельная или истёкшая cookie | Защищённые данные не возвращаются; API 401 |
| AUTH-02 | Пользователь A читает/меняет объект предприятия B | 404; запись/счётчики не изменились |
| AUTH-03 | A сравнивает свой проект с чужим | 404 без части чужого результата |
| AUTH-04 | Viewer выполняет update/import/delete/member-add | 403, состояние БД прежнее |
| AUTH-05 | Viewer без viewCost читает unpriced report/project list | Нет цен/бюджета в JSON, HTML, скрытых data-атрибутах |
| AUTH-06 | У участника отозван доступ при действующем JWT | Следующий запрос запрещён |
| AUTH-07 | Logout, затем повтор с прежней сессией | 401; другая вкладка не сохраняет доступ к данным |
| AUTH-08 | Switch A→B на одном устройстве | Ни на кадр не показываются кеш/черновик A |
| AUTH-09 | Document download по чужому ID | 404; файл не выдаётся |
| AUTH-10 | next=внешний URL либо protocol-relative URL | Переход только в безопасную локальную рабочую зону |
| AUTH-11 | Подмена enterpriseId/role в JSON | Привилегии/ownership не меняются |
| AUTH-12 | Изменяющий запрос с чужого origin | Отклонён принятой CSRF/origin-проверкой |

API-тесты запускаются с двумя синтетическими предприятиями и независимыми пользователями; нельзя использовать production для этих отрицательных проверок.

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Полноценный SSO, SCIM, публичная SaaS-регистрация, аудит безопасности сторонней инфраструктуры. Этот пакет не заявляет сертификацию системы.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
