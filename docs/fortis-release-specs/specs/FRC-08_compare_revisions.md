# FRC-08. Сравнение фиксированных вариантов одного предприятия

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Backend compare + frontend workspace/calculator.
**Зависимости для приёмки:** FRC-00, FRC-03, FRC-04, FRC-05, FRC-07.
**Цель:** Пользователь сравнивает две сохранённые версии по составу и бюджету, не принимая неизвестную эффективность за рассчитанную.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

Compare UI и вызов API уже есть в прочитанном workspace; это не новая функция с нуля. Пробел для проверки — фиксированность версий, объяснение суммы и честные ограничения сравнения. Расчёт эффективности/остаточного риска из более широкой предложенной Spec 03 не входит в данный пакет.

Источники: [C1], [S7], [S8], [S4]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `src/modules/workspace/ui/project-workspace-page.tsx`, `src/modules/defense-calculator/infra/backend-project-api.ts`; новый `src/modules/defense-calculator/ui/configuration-comparison.tsx`, domain compare tests.
BE: existing budget compare controller/service. Новые API-contract tests и `tests/integration/compare_revisions_test.go`.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Вход query: `projectIdA,projectVersionA,projectIdB,projectVersionB`. Новые названия параметров — предложение пакета; FRC-00 фиксирует явный адаптер существующих aliases. Выход `CompareResult`. Если financial capability отсутствует, priced endpoint 403; unpriced сравнение может показывать только отдельную разрешённую структурную проекцию, не скрывать цену CSS.

## 4. Требуемое поведение

1. Выбор только из доступного текущего предприятия. UI показывает названия, номера версий и дату сохранения. Изменение current state проекта не передвигает выбранную сравниваемую revision автоматически.
2. Сервер проверяет доступ к обеим сторонам до вычисления и выдачи данных. Разные предприятия → 400 incompatible_projects; тот же projectId допустим только для разных существующих revisions.
3. Таблица: общий итог, известная часть и полнота; число позиций/единиц; стоимость по реальным слоям и типам; бюджет/остаток; изменившиеся количества и цены; источники/дата/quality.
4. Разница всегда B−A. Процент `(B−A)/A×100` выводится только при полных итогах и A>0; округление display 2 знака. A=0 → «Не рассчитывается», а не Infinity. Unknown total → разница не вычислена.
5. Для агрегатов используются устойчивые layerId/assetId. Если варианты созданы независимо и ID не совпадают, не угадывать соответствие по похожему названию: показывать раздельные строки с пометкой.
6. Изменения цены каталога не переписывают сравнение старых revisions. Разные источники цен/даты видны как предупреждение о сопоставимости.
7. Не подписывать «эффективнее», «оптимальный», «достаточная защита» по меньшей цене или количеству объектов. Existing визуальная геометрия не превращается в достоверный процент защищённости.
8. Старый async result, ошибка одной стороны, permission change и смена предприятия не оставляют прежнее сравнение как новое успешное.

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Автоматический выбор лучшего варианта, вероятностное сравнение, многопроектная оптимизация, сопоставление геометрии/вооружения, новая система закупок.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
