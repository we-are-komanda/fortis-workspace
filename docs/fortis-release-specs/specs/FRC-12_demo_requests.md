# FRC-12. Заявка на демонстрацию: реальная запись и уведомление

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Frontend landing + backend public form + infrastructure.
**Зависимости для приёмки:** FRC-00, FRC-01.
**Цель:** Ни одна принятая интерфейсом заявка не теряется, а команда получает уведомление либо видит доставочный сбой.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

**Основание предыдущего аудита:** handler формы только переключал submitted state. В этом ходе форма не была повторно прочитана/отправлена. Кодер сначала воспроизводит отсутствие durable записи; если уже исправлено — оставляет работающий канал и добавляет недостающие проверки.

Источники: [S4]; новые публичные API/пороги — решения пакета. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `src/modules/home/ui/home-page.tsx`; новый `src/app/api/public/demo-requests/route.ts` и typed API helper.
BE новые: `internal/modules/demo_request/{domain,application,infrastructure,ui}/`, регистрация DI/router, миграции `demo_requests` и delivery outbox либо переиспользование уже существующего модуля.
Новые tests: BE integration заявок/идемпотентности и FE `test/playwright/demo-request.spec.ts`. Admin review — защищённый existing admin surface либо минимальный read-only admin endpoint; не новая CRM.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Same-origin POST `/api/public/demo-requests` → новый BE POST `/api/v1/demo-requests`. Input `DemoRequestInput`; header `Idempotency-Key`. Успех после durable commit: `201 {requestId,status:"received"}`; idempotent повтор → 200 с тем же ID. Уведомление асинхронно выполняет runtime приложения после приёма заявки; это требование реализации сервиса, не обещание фоновой работы ассистента.

## 4. Требуемое поведение

1. Поля: name 2–120 символов после trim, organization 1–200, email до 254 с валидным форматом, comment до 2000, consent=true, consentVersion из server allowlist опубликованного текста. Поля назначения email/notification не принимаются от клиента.
2. Текст согласия/политики предоставляет владелец продукта перед включением сбора; кодер не придумывает юридическое основание. Сохраняются версия текста и server timestamp согласия. Production-публикация формы без этих материалов заблокирована.
3. Запись заявки и событие уведомления — одна БД-транзакция. UI success только после commit. Сбой уведомления не делает уже записанную заявку потерянной и не просит пользователя создать дубль.
4. Outbox доставляет через один настроенный канал SMTP либо имеющийся approved provider. Новый внешний CRM не нужен. Delivery retries: 1, 5, 30 минут, затем каждый час до 24 часов; после этого failed с alert ответственному. Взятие события worker-ом атомарно, повторная отправка имеет одинаковый eventId. Не обещать exactly-once доставки внешней почты.
5. Получатель берётся из server config. Заявка остаётся в защищённом реестре со статусом pending/sent/failed, попытками и последней ошибкой без секретов. Должен быть назначенный человек, проверяющий failed.
6. Idempotency-Key + hash нормализованного input scoped к операции живёт 24 часа. Повтор того же payload/ключа возвращает прежний ID; другой payload → 409. Double click и потеря ответа не создают второй lead.
7. Rate limit: стартово 5 попыток/10 минут на доверенно определённый client IP и 3 принятые заявки/час на нормализованный email; distributed storage, не process memory в serverless. 429 с Retry-After. Значения — настройки релиза, не вечный продуктовый закон.
8. Same-origin/CSRF защита для browser form, лимит тела 16 KiB, нормализация и output escaping; запрет header injection. Email/comment/тело запроса и consent не пишутся в общий access log. Секреты SMTP только server env/secret storage.
9. Состояния: idle, submitting, success, validation error, retryable failure. На ошибке сохранять ввод; «Заявка получена. Номер…» только после DB acknowledgement. Обещания «свяжемся за час/24 часа» не добавлять без бизнес-обязательства.
10. Retention заявок и доступ операторов фиксируются владельцем данных в FRC-14; не бесконечное хранение по умолчанию.

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| LEAD-01 | Валидная форма | 201, DB row и outbox event, UI показывает ID |
| LEAD-02 | DB commit failure | 503; success state не наступает |
| LEAD-03 | Notification provider недоступен | Заявка существует, retry pending/failed виден ответственному |
| LEAD-04 | Повтор того же запроса после timeout | Тот же ID; один lead |
| LEAD-05 | Double click | Одна accepted запись |
| LEAD-06 | Нет consent/неизвестная версия/невалидный email | 400 с полями, DB row отсутствует |
| LEAD-07 | Лимит запросов превышен | 429 Retry-After, без дублирования lead |
| LEAD-08 | Публичный GET по чужому requestId | Нет персональных данных; реестр только admin |
| LEAD-09 | Comment с HTML/newline header payload | Безопасный текст; нет инъекции в письмо/лог |
| LEAD-10 | Публичная форма опубликована без notification config/consent text | Release check не пропускает публикацию |

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

CRM, лид-скоринг, массовые рассылки, обогащение контактов, автоматическое заключение договоров. Реальные письма/контакты для теста не используются.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
