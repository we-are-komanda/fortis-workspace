# FRC-13. CI и сквозная приёмка на настоящем backend

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** QA + frontend/backend + infrastructure.
**Зависимости для приёмки:** FRC-00, FRC-01, FRC-02, FRC-03, FRC-04, FRC-05, FRC-06, FRC-07, FRC-08, FRC-09, FRC-10, FRC-11, FRC-12.
**Цель:** Релиз принимается по воспроизводимому пользовательскому результату, а не только по зелёной сборке или mock UI.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

Тесты уже есть. Предыдущий аудит отметил isolated Playwright suite с перехватом всех API ответом 503; это полезная UI-проверка, но не real-backend E2E. Spec 00/03 требуют матрицу fixture→API→UI→отчёт. Задачу начать после FRC-00, а принимать после зависимостей — не откладывать написание тестов до конца.

Источники: [S4], [S7], [S8], [S6]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `package.json`, existing `test/playwright/` configs и specs; новая `.github/workflows/release-checks.yml`, `test/playwright/release.config.ts`, `test/playwright/release-flow.spec.ts`.
BE: существующий Makefile/unit/integration/e2e и новая CI job для ephemeral PostgreSQL/migrations.
Parent/knowledge-base: acceptance matrix, release evidence. Fixture `fixtures/finance-v1.json` копируется/подключается обеими сторонами без изменения expected values.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Новые предлагаемыe scripts: `test:unit`, `test:e2e:release`, `verify:release`; они должны вызывать реальные тесты, не echo/grep-success. `pnpm test:e2e:release` использует `PLAYWRIGHT_BASE_URL` и выделенные тестовые аккаунты/данные. BE profile: `go test -race -tags=unit ./...`, integration с настоящей БД, и HTTP E2E на поднятом процессе. Точные flags/tag существующей кодовой базы подтверждаются FRC-00.

## 4. Требуемое поведение

1. Два независимых набора: быстрые unit/isolated UI и release E2E. В позитивном release E2E не перехватывать auth, projects, assets, cost, budget, compare, report. Контрольная подложка карты может быть локальной синтетической, но бизнес-API/БД настоящие.
2. Pipeline: pinned dependencies → lint/typecheck → unit/golden → BE build+unit → migrate ephemeral DB → integration → FE production build → boot services → release E2E → evidence upload.
3. Настроить required checks для release branch/PR через разрешённый механизм. Проверить отдельно, что необходимая политика реально включена; наличие YAML не доказывает branch gate. Нельзя использовать подмену green status или blanket ignore errors.
4. Основной E2E: чистый пользователь с выданным предприятием → новая конфигурация → синтетические позиции в реальных UI формах → save → новая браузерная сессия → load → калькулятор → второй сохранённый вариант → compare → report. Все backend ответы проверяются на identity, суммы сверяются по golden fixture.
5. Отдельные suites: 409 двух сессий, offline/5xx recovery, budget race, changed prices, empty enterprise, revoked access, hideCost, document pipeline, accepted lead. Fault injection допускается только в отрицательной группе и маркируется; её нельзя выдать за happy-path доказательство.
6. Desktop regression `1280×720` и `1440×960`: selection, panels, legend, save errors, keyboard navigation, фокус модальных окон, табличная альтернатива карте. Не требовать нового mobile flow.
7. Проверить print actual PDF: не пустой, карта есть, строки/суммы/версия совпадают, hidden-cost поля отсутствуют. Скриншот и текстовая проверка нужны вместе.
8. Стартовые внутренние performance checks: synthetic проект 100 позиций/20 слоёв; 10 одновременных тестовых сессий. Метаданные/стоимость p95≤2 с, save p95≤3 с на документированном staging-окружении. Это предложенные gates, не опубликованный SLA. Отдельно записать CPU/RAM/DB/network, иначе числа не сравнимы.
9. Любой business correctness/access test FAIL блокирует релиз. Не переписывать fixture под ошибочную текущую сумму. Нестабильный тест не обходится repeat-until-green без разбора.
10. Acceptance evidence: FE/BE SHA, image digest, migrations, команды, результаты, trace/screenshots/PDF и время проверки. Токены, пароли, реальные карты и личные данные в artifacts не попадают.

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| CI-01 | Намеренно сломать unit/golden в тестовом PR | Required check красный, merge/release блокируется |
| CI-02 | Настоящий backend остановлен перед positive E2E | Suite падает; mocks не спасают |
| CI-03 | Чистый пользователь полностью проходит путь | PASS с реальными projectId/version и БД |
| CI-04 | Инъекция расхождения total на 1 копейку | Финансовый тест падает |
| CI-05 | Отчёт без карты или с ценой при hideCost | Suite падает |
| CI-06 | Ошибка изоляции A/B | Suite падает независимо от зелёного frontend build |
| CI-07 | Повторный чистый запуск на тех же SHA/fixtures | Тот же ожидаемый результат без ручной правки БД |
| CI-08 | Проверить artifact bundle | Достаточно доказательств и нет секретов |
| CI-09 | Разместить синтетический объект, изменить количество/координаты, скрыть/показать, удалить | Карта/список/калькулятор синхронны; после save/load значения и видимость сохранены |
| CI-10 | Изменить составной объект, сохранить/открыть и проверить отчёт | Существующие поля не потеряны; цена совпадает с золотым тестом |
| CI-11 | Изменить membership/бюджет/документ | В журнале правильный actor/entity/version без сырого payload |

Все тестовые изменения для CI-01/04 делаются только в изолированной проверочной ветке и не входят в релиз.

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Подмена настоящего API в happy-path, давление на production нагрузкой, фиктивная security-сертификация, мобильная переработка, абсолютные обещания uptime.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
