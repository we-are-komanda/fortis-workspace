# FRC-05. Единый расчёт стоимости по реальным размещениям

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Backend budget/cost + frontend calculator.
**Зависимости для приёмки:** FRC-00, FRC-04.
**Цель:** У карты, калькулятора и отчёта одна арифметика, одни строки и одна версия исходных цен.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

**Проверено в коде:** calculator совмещает локальные строки и fallback на backend total. Предлагаемая Spec 00 требует единый версионированный результат. Исторический контекст отмечает legacy mapping на 8 calculator-эшелонов. Подтверждение конкретного расхождения сумм должно быть получено тестом, а не предположением.

Источники: [C3], [S2], [S6], [S7]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `src/shared/lib/defense-project.ts`, `src/modules/defense-calculator/domain/costing.ts`, `project-asset-adapter.ts`, `project-report-lines.ts`, `structural-profile.ts`, `ui/calculator-page.tsx`, `infra/backend-project-api.ts`.
Новые FE: `domain/cost-projection.ts`, `domain/cost-projection.test.ts`.
BE: `internal/modules/budget/` и DTO расчёта; новый golden test по `fixtures/finance-v1.json`. Существующие unrelated scoring-функции не переписывать.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Вход: полный зафиксированный snapshot проекта и политики цен. Выход: `CostProjection` из общих контрактов. Старые поля `totalMln` и byEchelon допускаются только как derived compatibility output, не независимый расчёт. На FE `buildDraftCostProjection` строит явно черновой результат той же арифметикой; server projection принимается только при совпадении identity.

## 4. Требуемое поведение

1. Выделить функции точной арифметики и выбора цены, покрыть общим JSON golden fixture на FE и BE. Нельзя тестировать обе стороны одной и той же мок-реализацией.
2. Итерировать `project.placedObjects`; получать group по `layerId` из `project.layers`. Пользовательские слои включаются без кода L1–L9/таблицы на 8 старых эшелонов.
3. В каждой строке objectId, assetId, layerId, имя, количество, unit price, line total, источник цены. Quantity применяется один раз. Стоимость выбранного оборудования не выводится из площади/эффективности/покрытия.
4. Правила override, components, missing price, rounding и валюты — строго раздел 6 общего контракта. Нулевая override не должна пропасть из-за `||`.
5. Скрытые, inactive и maintenance позиции остаются в смете. Удалённые позиции исчезают из всех текущих проекций, но не из старой ревизии.
6. Пустой проект: пустые строки, нулевой итог, нулевые count; никакого legacy бюджета, каталожного списка или рекомендованных комплектов как результата.
7. Server-backed saved экран читает один CostProjection. Dirty экран либо показывает целиком draft preview, либо явно оставляет прежнюю сохранённую сводку в отдельном блоке; смешанная таблица запрещена.
8. Суммы строк, групп и итога сверяются в копейках. Отдельно зафиксировать область оценки: введённые цены, не выдуманный TCO/OPEX/НДС. Автоматический подбор закупок/ранжирование эффективности не входят в релизный расчёт.
9. Для старой ревизии calculationVersion/price snapshot фиксируются; обновление каталога или алгоритма не меняет выданный ранее результат без явного нового расчёта/версии.

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Оценка реальной защищённости, автоматический подбор оборудования, изменение критериев эффективности, построение новой финансовой ERP, учёт закупочных договоров.
