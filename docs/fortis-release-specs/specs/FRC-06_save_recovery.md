# FRC-06. Сохранение, локальный черновик и конфликт версий без потери данных

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Frontend project/variants state + QA.
**Зависимости для приёмки:** FRC-00, FRC-02, FRC-04, FRC-05.
**Цель:** Пользователь понимает, что сохранено, и не теряет работу при сетевом сбое, конфликте или переходе между экранами.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

Механизм вариантов и обработка 409 уже существуют по прошлому аудиту. ADR-0010 и Spec 00 требуют единый current context и отсутствие silent overwrite. Добавляем проверяемый lifecycle, а не новый параллельный store.

Источники: [S7], [S8], [S9], [S4]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `src/shared/lib/use-defense-project-store.ts`, `src/modules/drone-defense/domain/use-defense-variants-store.ts`, `ui/variant-selector.tsx`, `ui/variants-modal.tsx`, `ui/defense-studio-shell.tsx`, workspace и calculator.
Новые: `src/shared/lib/project-save-state.ts`, `project-save-state.test.ts`, `project-draft-storage.ts`, `project-draft-storage.test.ts`. DOM/браузерные тесты дополняют существующие, а не заменяются contract regex tests.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Вход: current project, saved ProjectRef, business-change counter локального draft, ответы save/load. Выход: `SaveStatus`, saved identity и user-scoped recovery. Для каждой in-flight операции хранятся отправленная revision и локальный change counter на момент старта; UI-выбор и тема не считаются бизнес-изменением.

## 4. Требуемое поведение

1. Один store для `/workspace`, `/prototype`, `/calculator`. Переключение страниц не создаёт отдельную конфигурацию.
2. Статусы отображаются явно: «Сохранено», «Есть несохранённые изменения», «Сохраняется», «Черновик на этом устройстве», «Конфликт версий», «Не удалось сохранить». Успешная localStorage запись не даёт статус server saved.
3. После edit обновить draft и локальный preview. Сервер сохраняется явным действием пользователя. В этом релизе не вводить автоматическое серверное сохранение/слияние.
4. Если во время save пользователь ещё менял данные, успешный ответ обновляет baseline server version, но сохраняет более новый локальный draft и статус dirty. Нельзя replaceProject старым отправленным payload поверх новых изменений.
5. На timeout/5xx сохранять draft, показывать retry, requestId; после неоднозначного результата сначала проверить server revision. Нет автоматического force overwrite.
6. На 409 оставить draft неизменным. Действия: открыть новую server version с подтверждением потери несохранённого, либо создать новый вариант текущего draft с разрешениями и идемпотентностью. Без автоматического объединения.
7. Scoped localStorage как в общем контракте. Migration старого общего ключа — только после явного подтверждения владельцем/доступа, не фоновая гидратация в аккаунт другого человека. Quota/security/corrupt JSON не должны ломать приложение: сообщить, что локальное восстановление недоступно; серверный draft в памяти не теряется.
8. Переход к другому проекту/предприятию/выходу с dirty state: сохранить, остаться, явно отказаться. При закрытии вкладки допустим browser beforeunload; не обещать, что браузер всегда даст диалог.
9. При logout и отзыве доступа не выводить данные чужой/старой сессии. Возможность recovery определяется пользователем и действующим доступом, а не наличием localStorage ключа.
10. Official report для dirty проекта предлагает сохранить или явно открыть документ последней сохранённой версии; default — сначала save. Локальный preview не называется официальным отчётом.

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| SAVE-01 | Edit → calculator → назад | Одна конфигурация, статус dirty, тот же draft |
| SAVE-02 | Save начат на edit 1; до ответа сделан edit 2 | Edit 2 остаётся; server version обновлена, статус dirty |
| SAVE-03 | Сервер записал, клиент потерял ответ | Проверка актуальной ревизии; нет дубликата/второго неявного save |
| SAVE-04 | Два пользователя начали с N; второй получил 409 | Его draft сохранён; нет silent overwrite |
| SAVE-05 | 409 → «Сохранить отдельным вариантом» | Новый projectId, старый серверный проект не изменён |
| SAVE-06 | JSON в localStorage повреждён / quota исчерпана | Понятная ошибка; приложение и server load работают |
| SAVE-07 | Theme/panel/selection изменились | Нет финансовой dirty-revision только из-за UI |
| SAVE-08 | Новый пользователь на том же устройстве | Не гидратирует чужой draft |
| SAVE-09 | Dirty → запрос отчёта | Нет смешения draft и saved; предлагается save либо явно last-saved |
| SAVE-10 | Потеря доступа при наличии draft | Дальнейшие reads/writes/exports блокируются согласно правам |

Новые pure-state тесты запускаются через `pnpm exec tsx --test src/shared/lib/project-save-state.test.ts src/shared/lib/project-draft-storage.test.ts`.

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

CRDT, realtime совместное редактирование, autosave с бесконечным replay, сохранение JWT в storage, автоприсвоение старых локальных проектов новому аккаунту.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
