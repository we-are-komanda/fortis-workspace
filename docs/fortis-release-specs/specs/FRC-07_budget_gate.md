# FRC-07. Бюджет проекта и атомарный запрет превышения

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Backend budget/project + frontend calculator/GIS.
**Зависимости для приёмки:** FRC-00, FRC-04, FRC-05, FRC-06.
**Цель:** Ни один сохраняемый путь изменения конфигурации не обходит установленный бюджет.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

ТЗ прямо содержит limited/unlimited и пример запрета превышения. Предложенные Spec 00/03 требуют серверную проверку. В прочитанном calculator есть отдельная проверка одного кандидата; она не доказывает enforcement всех операций. Выбранная политика пакета — hard limit без soft override.

Источники: [S1 раздел 1.1], [S7], [S8], [C3]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

BE: budget domain/application/ui, project create/import/update services и транзакции FRC-04; миграция current budget при необходимости.
FE: `src/modules/defense-calculator/infra/backend-project-api.ts`, `ui/calculator-page.tsx`, GIS placement/edit handlers и проектный save state. Новые BE integration `tests/integration/budget_revision_gate_test.go`; FE `domain/budget-projection.test.ts`.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

`BudgetConfig`, `BudgetProjection`, `BudgetUpdateRequest`, `BudgetCheckRequest` и `BudgetCheckResponse` — общие типы. `budget/check` принимает полный кандидат, а не только первую рекомендацию. Проверка read-only; финальное сохранение повторяет её внутри транзакции. 422 budget_exceeded/price_unknown возвращает field-level причину и не меняет revision.

## 4. Требуемое поведение

1. Источник лимита — серверный проект/его budget snapshot, не DEMO_BUDGET_MLN. Unlimited имеет limit=null; limited zero — допустимый нулевой лимит, не unlimited.
2. Перед добавлением/изменением пользователь видит предполагаемые расходы; при known limited overage активное изменение не применяется. Offline/непроверенный кандидат может сохраняться только как явно помеченный локальный draft, не как принятый server project.
3. Сервер проверяет полный итог после create, import, duplication, update quantity/price/composition, bulk changes и изменения самого лимита. Прямой API имеет те же правила, что UI.
4. Read budget → calculate → write current/revision должны выполняться согласованно: row lock либо корректный CAS внутри одной транзакции. Между budget-check и save другой пользователь не получает возможность «потратить один остаток дважды».
5. Равенство лимиту разрешено, превышение на одну копейку запрещено. Missing price при limited → 422 price_unknown. Unlimited разрешает предварительный неполный расчёт с предупреждением, а не итог 0.
6. Уменьшение лимита ниже текущего расхода запрещается. Переключение unlimited — отдельное явное действие с записью автора/старого/нового режима; это не скрытое подтверждение превышения.
7. Ошибка бюджета не очищает форму или другие несохранённые изменения. Показать требуемую сумму и остаток; не раскрывать чужие цены в error details.
8. Budget update увеличивает общую revision и создаёт snapshot. Старый отчёт читает старый лимит. Исторические импортированные превышения не исправляются фиктивно: помечаются как legacy-invalid, требуют явного изменения, не считаются принятыми рабочими конфигурациями.

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| BUD-01 | A=475 000, лимит 500 000, добавить 25 000 | Разрешено; остаток 0 |
| BUD-02 | Добавить 25 000.01 | 422; project, version, budget и revision count не изменились |
| BUD-03 | Превышение через прямой PUT/import/duplicate | Тот же запрет, не только disabled UI |
| BUD-04 | Два concurrent кандидата по 20 000 при остатке 25 000 | Один accepted; другой 409/после перечитывания 422; итог не превышен |
| BUD-05 | Limited с неизвестной ценой | 422 price_unknown |
| BUD-06 | Unlimited с неизвестной ценой | Draft/preliminary mark; total=null, не ложный ноль |
| BUD-07 | Снизить лимит до 400 000 у A | Отказ, прежний лимит/версия сохранены |
| BUD-08 | Изменить лимит с 500 000 на 600 000 | Новая общая revision; отчёт старой версии остаётся с 500 000 |
| BUD-09 | Скрыть объект на карте | Остаток не меняется |
| BUD-10 | Ввести 0 limited | Это нулевой лимит; платная позиция запрещена |

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Оптимизация состава, автоматическая рекомендация закупок, оценка достаточности защиты, soft-limit подтверждения, платёжные интеграции.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
