# FRC-09. Происхождение данных и безопасные документы библиотеки

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Backend assets/documents + frontend library + product data owner.
**Зависимости для приёмки:** FRC-00, FRC-02, FRC-04.
**Цель:** Каждая используемая карточка и цена имеют понятный источник; документы сохраняются и выдаются с корректными правами.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

CRUD библиотеки и documents API уже предусмотрены контекстом и прошлым аудитом. Spec 01 предложена, а не принята как реализованная. Здесь — только происхождение, приватность, документы и сохранность существующих полей; не разработка новых расчётных моделей оборудования.

Источники: [S10], [S7], [S1 раздел II], [S2]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

FE: `src/modules/drone-defense/ui/asset-library-manager.tsx`, `infra/asset-library-api.ts`, `infra/asset-documents-api.ts`, existing shared asset types.
BE: `internal/modules/defense_asset/`, document metadata/storage, existing `defense_asset_documents` migrations; новые provenance/doc-version поля и тесты в owning modules.
Новые FE: provenance form/presentation в существующем модуле; fixtures со синтетическими файлами и контрольными checksum.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

`DataProvenance` и DataQuality `confirmed|estimated|demo` — общие контракты. У старых данных provenance=null, UI «Источник не указан», а не автоматическое confirmed. Цена и существенные поля могут иметь отдельные записи происхождения; DTO позволяет fieldProvenance map, но существующий тип карточки не заменяется несовместимым новым форматом.

## 4. Требуемое поведение

1. Добавить источник, дату источника, дату/автора внесения, quality и revision. Присвоение confirmed требует ссылки/документа либо описания источника и даты; пометка означает подтверждение ответственным пользователем, не независимую сертификацию Fortis.
2. Пользователь видит качество данных рядом с ценой/карточкой. Прежние demo seed остаются demo даже после импорта в рабочее предприятие. Они могут использоваться только в явно предварительном документе; настоящий клиентский результат требует замены источниками клиента.
3. Обновление template не меняет instance overrides и уже сохранённые revisions. Обновить данные конкретного проекта — отдельное действие с preview изменений, последующим новым save/version.
4. Зафиксировать source document ID/revision/checksum в snapshot. Старую revision не заменяет новый файл с тем же названием. Документ можно удалить из активной библиотеки по правам; уже выданный отчёт не получает другой документ вместо исходного. При недоступности источника — честная пометка.
5. Начальный upload allowlist: PDF, PNG, JPEG, TXT; до 10 MiB. Это выбранная граница релиза, а не утверждение об ограничении ТЗ. Неподдерживаемые форматы дают 415, превышение 413. MIME сверяется с фактическим содержимым; имя очищается, storage key генерируется сервером.
6. Приватное объектное хранилище; download проходит backend permission check каждый раз, не постоянный публичный URL. Проверяются parent asset и enterprise. Доверять одному documentId нельзя.
7. Upload идёт в quarantine до проверки содержимого/антивредоносного сканирования. При недоступной проверке файл не публикуется. Конкретный scanner выбирается по инфраструктуре FRC-14; release gate требует успешной проверки реального pipeline. Не утверждать, что checksum выполняет роль антивируса.
8. Не загружать произвольный sourceUrl сервером: это метаданные источника, не универсальный fetch-proxy. Render описаний/имён текстом, не raw HTML.
9. Report hideCost исключает финансовые структурированные поля и ссылки на коммерческие документы из export package; свободный текст/вложения требуют отдельного просмотра и не объявляются автоматически очищенными.
10. Отдельная матрица lossless round-trip существующих типизированных карточек: проверка хранения, не разработка новых ТТХ/режимов применения.

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| DATA-01 | Старая карточка без source | Видно «Источник не указан», не confirmed |
| DATA-02 | Попытка confirmed без источника/даты | Field validation, статус не повышен |
| DATA-03 | Demo карточка импортирована | Quality остаётся demo |
| DATA-04 | Цена template обновлена после сохранения A7 | A7 прежняя; explicit refresh → новый draft/версия |
| DATA-05 | Загрузка >10 MiB / неверный MIME | 413 / 415; нет опубликованного файла |
| DATA-06 | Подозрительный файл / scanner unavailable | Quarantine/rejected; download не выдаётся |
| DATA-07 | Download пользователем другого предприятия | 404; public URL отсутствует |
| DATA-08 | Название/описание с HTML | Отображается безопасным текстом |
| DATA-09 | Файл заменён новой версией с тем же именем | Старый report source не начинает ссылаться на новую версию |
| DATA-10 | Существующая карточка с instance overrides прошла save/load | Все значения сохранены; template не изменён |

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Импорт всего рынка/каталога, сбор цен веб-скрейпингом, автоматическая достоверность ТТХ, новая иерархия каталогов, расчёты эффективности.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
