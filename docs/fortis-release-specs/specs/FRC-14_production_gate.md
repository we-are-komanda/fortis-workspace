# FRC-14. Эксплуатация, восстановление и решение о выпуске

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Infrastructure / Tech Lead / владелец продукта и данных.
**Зависимости для приёмки:** FRC-00, FRC-01, FRC-02, FRC-04, FRC-12, FRC-13.
**Цель:** Дать ограниченному кругу клиентов рабочий сервис, который можно наблюдать, восстановить и безопасно обновлять.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

Предыдущий аудит не выполнял backup restore, нагрузочный тест и не установил работающий backend SHA. Наличие probes/metrics в коде не означает, что настроены уведомления/backup. Это проверки неизвестного состояния с доработкой только отсутствующего.

Источники: [S4], [S7], [S8], [S9]; RPO/RTO и topology gate — решения пакета. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

BE существующие probes, metrics, config, Docker/compose/deployment; FE env/build configuration; инфраструктурные конфиги approved hosting и storage.
Новые parent: `docs/operations/runbook.md`, `docs/operations/restore-drill.md`, `docs/releases/2026-09-20/go-no-go.md`, безопасный configuration checklist. Новые monitoring/backup файлы живут в выбранном owning infra контуре, не содержат секретов.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Manifest FRC-00, результаты FRC-13, список критичных операций, release owner/on-call и согласованная поставка. Выдаёт go/no-go запись с приложенными доказательствами. Внешние подписки/оплата/production deployment не выполняются кодером без разрешения владельца.

## 4. Требуемое поведение

1. Утвердить одну топологию поставки: frontend, backend, БД, documents storage, secrets, notifications. Условия хостинга допускают коммерческое использование. Выбор провайдера, региона и политики данных подтверждает владелец; не выдавать Vercel production label за приёмку.
2. TLS на публичном и межсервисном пути вне localhost; secret manager/защищённая env. Удалить unsafe default credentials, debug endpoints и логи с body/token. CORS/CSRF согласованы с same-origin контрактом.
3. Liveness отвечает за процесс; readiness проверяет критичные зависимости и совместимость миграций; build metadata показывает версии без секретов. Внешняя поддержка имеет только нужный ей доступ.
4. Метрики: request/error rate, latency, save failures, 409 отдельно от outages, report failures, outbox pending/failed, storage/DB health. Correlation requestId сквозной FE BFF→BE. Несколько подряд ошибок synthetic health/readiness отправляют alert ответственному; получатель и проверка доставки обязательны.
5. Backup охватывает БД, revisions, необходимые report data и documents/storage metadata, а не только volume текущего проекта. Шифрование, ограниченный доступ и separate failure domain. Базовые предлагаемые критерии закрытой поставки: RPO≤24 ч, RTO≤4 ч. Это внутренние пороги; если заказчик требует строже, пакет не подтверждает его SLA.
6. Провести restore drill в отдельном окружении: восстановить проект, пользователей/permissions, revision, attachments; проверить checksum и суммы эталонного отчёта, войти, прочитать snapshot. Просто наличие backup файла не считается.
7. Миграции применяются одним контролируемым job, не конкурентно каждым instance. Rollback описывает отдельно приложение и данные: не откатывать destructive schema автоматически после начала клиентских writes. Иметь backup перед несовместимой миграцией и проверенный путь roll-forward.
8. Утвердить retention проектов/ревизий/отчётов/заявок/backup и удаление. Это отсутствующая бизнес-политика, не значение, которое разработчик выбирает молча. Demo данные хранятся отдельно от клиентских. Local draft policy учитывает shared devices.
9. Согласовать внешние зависимости карты/шрифтов/документов, куда уходят сетевые запросы и допустимо ли это для данных клиента. Не публиковать реальные объекты в demo, публичном репозитории или тестовом trace.
10. Короткая инструкция пользователю: вход, выбор проекта, save-state, что означает preliminary, создание вариантов/отчёта, обращение с requestId. Назначен человек поддержки и продуктовый ответственный за данные/цены.
11. Финальное go/no-go: все blocking FRC accepted на согласованных SHA, restore доказан, leads не теряются, customer data approved. Выдать небольшой группе пользователей, а не включать незавершённые модули массово.
12. Отслеживать только события продукта без содержимого проектов: успешный save/load/compare/report и ошибка с technical category. Не собирать геометрию, цены, тексты и названия в продуктовую телеметрию. Цель — проверить использование и возвращение, а не обещать метрики заранее.

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| OPS-01 | Staging backend/DB недоступны | Readiness/alert срабатывают; production write не подменяется mock |
| OPS-02 | Restore drill из backup | Проект/ревизия/документы/права восстановлены; checksum/суммы совпали |
| OPS-03 | Потеря доступа notification provider | Failed/pending видны; alert у ответственного |
| OPS-04 | Release rollback rehearsal | Описанный безопасный путь, без потери новых пользовательских данных |
| OPS-05 | Сверка deployed build metadata | Совпадает с manifest FRC-00 |
| OPS-06 | Проверка public logs/traces/build/env artifacts | Нет секретов, PII и реальной проектной геометрии |
| OPS-07 | Нет владельца поддержки/retention/данных | NO-GO с конкретной причиной, не формальное accepted |
| OPS-08 | Все gates пройдены | Заполненный go/no-go с датой, ответственными и evidence; никаких незакрытых critical defects |

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Обещанный SLA 99.9%, геораспределённый enterprise-кластер без требований, автоматическая юридическая сертификация, закупка сервисов без согласия, публикация клиентских данных.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
