# FRC-00. Закрепить проверяемый комплект релиза

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Tech Lead / infrastructure / knowledge-base.
**Зависимости для приёмки:** Нет.
**Цель:** Получить одну воспроизводимую исходную точку для всех исполнителей и отделить новые задачи от уже выполненных.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

**Проверено:** frontend/develop указывает на `7ae48358…`; roadmap содержит июльские изменения и откаты UI. **Предыдущий аудит:** версия workspace и deployment различалась; фактический backend SHA не был установлен. Разница «104 коммита» не считается повторно измеренной в этом пакете. Нельзя назначать все старые FRT как открытые по историческому system-prompt.

Источники: [S2], [S4], [S5], [S6]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

Существующие: parent `.gitmodules`, `README.md`, `AGENTS.md`; `knowledge-base/00_Index.md`, `Продуктовый_план_Fortis.md`; frontend `package.json`, `pnpm-lock.yaml`; backend `go.mod`, `Dockerfile`, `migrations/`.

Новые: parent `docs/releases/2026-09-20/release-manifest.json`, `docs/releases/2026-09-20/acceptance-matrix.md`; knowledge-base `01_Requirements/Release_2026_09_20_Index.md` с ссылками на этот пакет.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Выдаёт release manifest: repository URL, branch, commit SHA каждого submodule, deployment ID frontend, image digest и commit backend, фактически применённые миграции, версии Node/pnpm/Go, режим runtime, список названий требуемых env без значений. Если существующая поставка не раскрывает backend SHA, сначала добавить безопасную внутреннюю build metadata и повторно собрать; не угадывать его по ветке.

## 4. Требуемое поведение

1. Сделать read-only инвентаризацию checkout, refs и окружений. `git fetch` не равен `git pull`: не вливать изменения и не сбрасывать worktree автоматически.
2. Выбрать release baseline, согласовать соответствующие FE/BE контракты. Местом истины является manifest, а не «последняя main».
3. Сопоставить каждую FRC с существующими задачами. Исторические FRT-47/50/51/56/19/28 и FRT-70/71/72 — кандидаты на связь, не подтверждённый список незакрытого. Прочитать актуальное описание/статус перед переносом в tracker. В рамках этой спеки новые тикеты не требуются, если есть подходящий.
4. Ввести статусы матрицы `not_verified`, `failed`, `implemented`, `verified`, `accepted`. Для accepted обязательны SHA, сценарий и результат.
5. Выделить два набора: production blockers этого пакета и требования полного ТЗ за его границами. Поздние модули не попадают в релиз под видом исправлений.
6. Воспроизводимость проверяется в новом каталоге по закреплённым SHA, не через изменение текущего рабочего checkout пользователя.

## 5. Приёмка и регрессионные сценарии

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| BASE-01 | Чистый checkout manifest | Все репозитории на указанных SHA; нет «подхватить latest» |
| BASE-02 | Сравнить metadata работающих служб с manifest | Совпадение FE/BE; несовпадение блокирует приёмку |
| BASE-03 | Просмотреть manifest и артефакты | Нет токенов, паролей, cookie или customer data |
| BASE-04 | Исторически закрытая функция проходит текущий тест | Связана с существующей задачей; не переписывается |
| BASE-05 | Не установлен backend SHA | Явный blocker, не предположение о ветке |

Сдача этой задачи не означает production-ready; она даёт корректную базу остальным.

## 6. Порядок реализации

- [ ] Прочитать эту спеку, общие контракты и указанные исходные файлы. Проверить чистоту рабочего дерева; не сбрасывать чужие изменения.
- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Обновление framework, новый дизайн, массовый merge веток, перенос исходников в parent, изменение production без отдельного разрешения.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
