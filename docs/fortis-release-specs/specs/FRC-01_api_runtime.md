# FRC-01. Надёжная граница frontend–backend и явный demo-режим

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Frontend infra + backend + infrastructure.
**Зависимости для приёмки:** FRC-00.
**Цель:** Рабочие API возвращают настоящие данные или понятную ошибку; демонстрационные данные никогда не маскируют отказ.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

**Проверено в коде:** facilities route возвращает mock-данные при пустом результате и upstream 401/404. **Предыдущий аудит:** 502 на auth/me и projects; причина не установлена и здесь не воспроизведена. Задача не сводится к замене адреса сервера без диагностики.

Источники: [C2], [S4], [S9]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

Существующие FE: `src/modules/drone-defense/infra/backend-proxy.ts`, `next.config.ts`, `src/shared/lib/api-client.ts`, `src/app/api/auth/*/route.ts`, `src/app/api/defense/facilities/route.ts`, `src/app/api/defense/projects/**/route.ts`, остальные mock routes.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Потребляет runtime mode и envelope из общих контрактов. Выдаёт единый серверный resolver `resolveBackendBaseUrl()` и безопасную нормализацию ошибок. Same-origin `/api/v1` и `/api/defense` используют одинаковый источник конфигурации и правила forwarding. URL возвращается только серверному коду, а не браузерному store.

## 4. Требуемое поведение

1. В workspace-mode обязательна явная server env `BACKEND_URL`; старые FORTIS env допускаются как документированные aliases только если значения не конфликтуют. Несогласованные значения → configuration error. Никакого fallback на публичный IP; plain HTTP допускается только для явного localhost теста.
2. На production readiness требует корректный workspace-mode и backend connection; публичный лендинг может оставаться доступным. Отсутствующая конфигурация возвращает 503, не локальный mock.
3. Нормализовать один `/api/v1`, trailing slash и query. Авторизация пробрасывается только на закреплённый backend host. Cookie/Authorization не пересылаются на URL из пользовательского ввода.
4. Общий таймаут обычного API — 10 секунд; для документов — 30 секунд. Это стартовые ограничения пакета, конфигурируемые сверху, без бесконечных ожиданий. Запись не ретраится автоматически без идемпотентности.
5. Пустой список → 200 и пустой список. 401/403/404 сохраняют смысл. HTML/пустое тело от error upstream не должны превращаться в исключение JSON.parse с потерей исходного HTTP статуса. Некорректный success JSON → 502.
6. Если upstream недоступен — ошибка с requestId и пользовательским «Не удалось связаться с сервером». Подробности сети доступны только в очищенном журнале.
7. Mock-функции могут вызываться только в явно заданном demo-mode. Query, cookie пользователя и localStorage не переключают этот режим. Локальный recovery draft рабочего проекта не переименовывается в demo.
8. Проверять правильность поведения через настоящий HTTP stub только в интеграционных тестах; зелёный рабочий E2E позднее обязан идти на настоящий BE.

## 5. Приёмка и регрессионные сценарии

| ID | Вход | Ожидание |
|---|---|---|
| API-01 | Enterprises отвечает 200, items=[] | 200, items=[], totalItems=0; нет facility-alpha |
| API-02 | Upstream 401, тело HTML | 401 normalized error; mock не вызывается |
| API-03 | Upstream 403/404/409 JSON | Смысл/код сохранены, без превращения в общий 502 |
| API-04 | Upstream connection refused | 503 с requestId, ограниченное время, черновик сохранён |
| API-05 | Upstream не отвечает | 504 в пределах таймаута + небольшой запас транспорта |
| API-06 | Upstream 200 с некорректным JSON | 502; UI не показывает успешную загрузку |
| API-07 | Отсутствует BACKEND_URL в workspace | Readiness отрицательная, API 503; нет fallback IP |
| API-08 | Две настройки URL конфликтуют | Окружение не принимается; диагностируемая конфигурационная ошибка |
| API-09 | Demo mode, запрос списка | Только синтетические данные; ответ/экран помечены demo |
| API-10 | Ошибка записи после отправки | Нет неограниченного auto retry; результат проверяется по правилам FRC-04/06 |

Команда профильного нового теста: `pnpm exec tsx --test src/modules/drone-defense/infra/backend-proxy.release.test.ts`.

## 6. Порядок реализации

- [ ] Для каждого сценария раздела 5 добавить либо найти автоматическую проверку. Существующее зелёное поведение не реализовывать повторно.
- [ ] Воспроизвести ожидаемый дефект на закреплённой версии либо отметить требование как уже выполненное со ссылкой на проверку. Для нового поведения сначала получить падающий тест.
- [ ] Внести минимальное изменение в owning repository; обновить DTO/OpenAPI и миграции только там, где они затронуты этой задачей.
- [ ] Запустить профильные тесты, линтер и сборку; приложить команды, SHA и результат. Статические проверки исходного текста не заменяют behavioural-тест.
- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.
