# FRC-04. Lossless save/load и неизменяемые серверные ревизии

**Статус:** проект спецификации от 20 сентября 2026 года; не отметка о выполнении.
**Ответственный контур:** Backend project persistence + frontend DTO.
**Зависимости для приёмки:** FRC-00, FRC-01, FRC-02.
**Цель:** Любое успешно сохранённое состояние можно открыть без потери полей и однозначно использовать для расчёта, сравнения и отчёта.
**Архитектура:** доработка существующих модулей Fortis; границы frontend/backend/knowledge-base сохраняются. Общие определения — в `../00_SHARED_CONTRACTS.md`, типы — в `../contracts/release-contracts.ts`.
**Стек:** существующие Next.js / React / TypeScript / Zustand и Go / PostgreSQL / GORM. Версии определяются закреплённым комплектом FRC-00; обновление стека не входит в задачу.

## 1. Основание и границы достоверности

Save/load и optimistic locking уже присутствовали в предыдущем аудитe. Источники требуют версию результата, но наличие счётчика version не доказывает наличие неизменяемой истории. **Новые решения пакета:** revision storage и идемпотентное создание. Потеря отдельных полей при round-trip — обязательная проверка, не объявленный без теста дефект.

Источники: [S7], [S8], [S9], [S10], [S4]. Их статусы и ссылки собраны в `../SOURCES.md`. Требования ниже, которых нет в источниках, являются предлагаемыми решениями этого релиза, а не уже принятыми ADR.

## 2. Файлы и зоны изменения

BE: `internal/modules/defense_project/domain/`, `application/defense_project_service.go`, `infrastructure/defense_project_repository.go`, `ui/controller.go`, соответствующие DTO/mappers; migrations.
Новые BE: revision repository/model в owning-модуле; миграция `project_revisions` и idempotency records; `tests/integration/project_revision_roundtrip_test.go`.
FE: `src/shared/types/defense-project.ts`, `src/modules/drone-defense/infra/api-client.ts`, используемые import/export adapters. Новая fixture собирается из существующего конструктора проекта, не из урезанного finance fixture.

Существующие пути — точки входа, а не разрешение переписать весь модуль. Предлагаемые новые пути явно названы новыми. Если FRC-00 обнаружит перенос файлов, обновить адреса в этой спеке, сохранив функциональные границы.

## 3. Входные и выходные контракты

Выдаёт сохранённый `ProjectRef`, полную ревизию envelope `{project,budget,inputDataVersions}` и `snapshotDigest`. Дополяет existing get/export query `projectVersion`. Цена/происхождение из FRC-09 входят в frozen snapshot при появлении, но отсутствие новых необязательных полей не ломает старые проекты. Типы в `contracts/release-contracts.ts` — общая терминология, не замена всех текущих DTO.

## 4. Требуемое поведение

1. Явно перечислить сохраняемые поля текущего DefenseProject по runtime-типам: layers/geometry, assetLibrary, placedObjects, instance overrides, составные профили, видимость, заметки и пользовательские поля. Сравнить FE→BE→DB→BE→FE. Нельзя терять поля молча из-за неполного mapper.
2. Не использовать неизвестные extension-поля для прав/стоимости/ownership. Дополнительные безопасные данные сохраняются без повышения привилегий; неподдерживаемая schemaVersion отклоняется, а не частично импортируется.
3. Один transaction: проверка доступа и version → проверка invariants/бюджета (FRC-07) → запись current state → version+1 → immutable revision. При любом сбое всё откатывается.
4. В migration создать snapshot лишь текущей известной версии каждого проекта. Уникальность projectId/version; budget в revision соответствует именно моменту save. Старый снимок не получает новую цену из глобального каталога.
5. POST create/import поддерживает scoped Idempotency-Key: один проект при double-click/timeout retry. Сравнение payload при одинаковом ключе обязательно. Ключ хранится 24 часа; это выбранный срок технической защиты, не политика клиентских данных.
6. Для UPDATE expected version обязательна; после успешного write возвращается новая version из БД. Безусловный overwrite, last-write-wins и повышение version на клиенте запрещены.
7. Запрос конкретной старой версии возвращает её либо revision_not_found; нельзя молча выдавать current.
8. Удаление проекта запрещает доступ к revisions обычным пользователям; политика soft delete/retention фиксируется поставкой FRC-14. Права повторно проверяются на historical reads и idempotent replay.
9. Изменение бюджетного лимита через существующий budget API позднее использует ту же revision-транзакцию. Прямой отдельный write budget_configs без revision недопустим в принятом релизе.

## 5. Приёмка и регрессионные сценарии

| ID | Сценарий | Ожидание |
|---|---|---|
| REV-01 | Создать проект с пользовательским layer ID, polygon, overrides, заметками, compoundProfile и visibility | После load все бизнес-поля совпадают; времена/серверные ID сверяются отдельно |
| REV-02 | Модифицировать библиотечный шаблон после save | Ревизия проекта не изменилась |
| REV-03 | Два сохранения с одной expected version N | Один success N+1, другой 409; нет N+2 от stale клиента |
| REV-04 | Ошибка вставки revision после обновления current | Rollback current/budget/version, новая ревизия отсутствует |
| REV-05 | Повторить POST с тем же Idempotency-Key и payload | Один projectId, один результат |
| REV-06 | Тот же ключ, другой payload | 409 idempotency_conflict |
| REV-07 | Запрос revision до точки migration | 404 revision_not_found; нет фиктивной истории |
| REV-08 | Удалить/отозвать доступ, затем обратиться к старой revision | Доступ не обходится |
| REV-09 | Сохранить старый проект schemaVersion=1 | Совместимый load; новые поля null/явные defaults, не demo |
| REV-10 | Модель использует км на API и м на FE | Round-trip без масштаба ×1000/÷1000 повторно |

Проверка выполняется на настоящем PostgreSQL, не только на in-memory mock repository.

- [ ] После интеграции пройти релевантный сценарий на release-кандидате с реальным backend. Не использовать реальные клиентские данные для отрицательных тестов.
- [ ] Обновить матрицу приёмки и knowledge-base. После коммитов в дочерних репозиториях обновить parent pointers отдельным согласованным изменением.

## 7. Не входит в задачу

Автоматический merge конфликтов, редактирование исторической ревизии, event sourcing всего приложения, восстановление выдуманной истории, изменение алгоритмов геометрии/покрытия.

## 8. Что приложить к сдаче

PR или commit в каждом изменённом репозитории; перечень реализованных сценариев с PASS/FAIL; команда запуска проверок; версия окружения; миграция/откат при изменении хранения; скриншоты затронутых UI-состояний без секретов; обновлённые контракты и пункт матрицы приёмки. Нельзя закрывать задачу только по наличию кнопки, маршрута или HTTP 200.
